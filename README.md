> 三个可运行的 AI 产品 Demo，覆盖「理解大模型 → 把方法论做成工具 → 在具体行业落地」这条完整链路。

## 一、三个项目不是并列关系，是一条线

```
  理解模型能力边界              把方法论产品化                在强合规行业落地
        │                            │                            │
        ▼                            ▼                            ▼
  openclaw-mvp          →       doc-buddy          →      medical-triage-agent
  （Agent 运行时）            （AI 文档搭子）            （医疗智能导诊助手）
        │                            │                            │
  亲手实现工具调用、        把「怎么写 BRD/MRD/PRD」      把同样的思路用在医疗：
  上下文压缩、终止判定      固化成可复用的生成链路        安全必须靠机制而非提示词
        │                            │                            │
        └────────── 知道模型会在哪里失败 ──────────┘
                              ↓
                    所以产品里要提前设防
```

**为什么这样排**：第一个项目让我知道大模型真实的失败模式（工具调用失败、上下文超限、结果不可复现）；
第二个项目是我在知道这些之后，为"输出不稳定"设计的解法；
第三个项目把前两者的经验放进一个容错率为零的行业——医疗。

## 三、逐个说明

### 1. openclaw-mvp — 从零实现 Agent 运行时

不调用任何 Agent 框架，用 TypeScript 手写完整循环：

```
指令接收 → 上下文构建 → 模型推理 → 工具调用 → 结果回流 → 终止判定
```

内置 5 个工具（文件读写、命令执行、记忆存取），实现跨会话长期记忆与 token 超阈值时的自动压缩，
附带双栏 Web UI（SSE 流式输出 + 分色日志 + token 进度条）和 CLI REPL 两种交互方式。

**这个项目解决的是我自己的问题**：作为产品经理，我想知道"模型哪一步会失败、成本花在哪"，
最直接的办法就是自己写一遍。写完之后再和研发讨论上下文窗口、工具调用失败率，就不会说外行话。

→ [查看详细说明](./openclaw-mvp/README.md)

### 2. doc-buddy — AI 文档搭子（BRD / MRD / PRD）

**起因**：我先手写完了企业级 AI 产品 SmartTender 的 BRD、MRD、PRD 全套文档，
发现三类文档的输入其实是同一份需求信息，只是视角不同——于是把这套写法做成了工具。

| 文档 | 读者 | 回答什么 | 结构 |
|------|------|----------|------|
| **BRD** | 决策层 / 资源审批方 | 为什么值得做 | 商业背景、成本收益与 ROI、In-Scope / Out-of-Scope、风险合规、Go / No-Go 建议 |
| **MRD** | 产品与市场团队 | 凭什么赢 | TAM/SAM/SOM、用户分层与画像、痛点 KANO 分类、竞品对比与启示、差异化定位 |
| **PRD** | 研发 | 怎么做 | 10 章标准结构、功能优先级、Mermaid 流程图、数据需求、里程碑 |

**核心难点是"大模型输出不稳定"，解法是三层收敛**：
- 引导层：基于「新 5 要素」模型做完整性校验，且规定追问**必须携带选项或场景示例**（禁止"请问你的痛点是什么"这类直白提问）
- 生成层：固定章节结构与图表规范
- 解析层：JSON 容错（如模型常见的尾逗号），失败走降级路径，不把错误结果交给用户

每次模型调用的提示词版本、输入输出、token、耗时、状态全量落盘到 `logs/`，用日志驱动提示词迭代。
支持 Markdown / Word / PDF 三种导出。

→ [快速开始](./doc-buddy/README.md)

### 3. medical-triage-agent — 医疗智能导诊助手

**起点不是从零搭建，而是接管一个跑不通的工作流**：原流程 14 个节点，
逐节点核对后定位 4 处致命断线（合规分支无出口、知识库召回判断接反、工具调用节点缺失、
意图判定 false 分支悬空）与 9 项配置缺陷，重构成 25 节点 / 28 连线的可运行流程。

**核心设计是三道防线**：

| 防线 | 机制 | 为什么这样做 |
|------|------|--------------|
| 入口 | 13 类危急信号规则 + 三类语境排除 + PII 脱敏 | 漏判代价不对称，规则保证零漏判，模型用于降误报 |
| 中间 | 四类意图分流（知识库问答 / 院内业务 / 导诊 / 闲聊） | 高频导诊问法走模板直出，不调模型，更快且零幻觉 |
| 出口 | 6 类禁用表述正则拦截 + 强制免责声明 + 思维链剥离 | 提示词是"请求"，代码是"保证"——医疗产品里这两者不能混 |

设计 8 条测试路径（危急真阳性、业务查询、知识库命中、未命中兜底、越界要药、闲聊、
否定语境、罕见病转人工）并逐条实测通过。

→ [查看完整诊断与修复记录](./medical-triage-agent/优化说明与使用指南.md)

## 四、安全说明

- **本仓库不含任何 API Key**。`doc-buddy/config.js` 已在 `.gitignore` 中排除，
  请复制 `config.example.js` 为 `config.js` 后自行填写，或使用环境变量 `GLM_API_KEY`。
- 医疗工作流为**演示用途**，不构成任何医疗建议；知识库内容来自公开的政策文件与专家共识。

## 五、本地运行

三个项目互相独立，可分别运行：

```bash
# 1. Agent 运行时
cd openclaw-mvp && npm install && npm run server

# 2. AI 文档搭子
cd doc-buddy && npm install && cp config.example.js config.js  # 填入 API Key
node server.js

# 3. 医疗导诊助手（需本地 Dify 环境）
#    在 Dify 中导入 medical-triage-agent/医疗AI-Workflow-安全增强版.yml
#    另开终端启动模拟接口：
cd medical-triage-agent && python hospital_mock_server.py
```
