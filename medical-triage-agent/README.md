# medical-triage-agent · 医疗智能导诊助手

基于 Dify 1.15.0 的医疗问答工作流。核心不是"搭一个能聊的机器人"，
而是**把医疗场景里的安全要求变成结构上不可能绕过的机制**。

---

## 起点：接管一个跑不通的工作流

原流程 14 个节点，看起来完整，逐节点核对后定位 **4 处致命断线**：

| # | 问题 | 后果 |
|---|------|------|
| 1 | 正常回答路径的「合规」分支没有出口 | 走到最后直接空输出 |
| 2 | 知识库召回判断分支接反（`empty=true` 反而去走检索） | 命中与未命中的逻辑完全颠倒 |
| 3 | 设计稿里的「工具调用 HTTP-Request」节点在应用中不存在 | 业务查询路径实际是断的 |
| 4 | 意图判定分支只有 `true` 一条出边，`false` 悬空 | 未命中意图时流程终止无响应 |

另有 9 项配置缺陷：判定节点温度设 0.7、`contains` 匹配带标点的整句、
急救话术被截断成"立即拨打120，就近急"（丢了"诊"字）、提示词错别字、
无患者信息脱敏、无召回相似度阈值、无审计日志、无反馈入口、
免责声明仅靠提示词约束（模型不遵守就没人拦得住）。

重构后：**25 节点 / 28 连线**。

## 三道防线

```
患者提问
   │
   ▼
┌─ 入口：安全护栏（代码节点）─────────────────┐
│ · 13 类危急信号规则（急性胸痛、呼吸困难、     │
│   意识障碍、大出血、中毒、自伤…）零漏判筛查   │
│ · 三类语境排除降误报：否定语境「没有胸痛」/   │
│   既往史「三年前」/ 疑问句式「胸痛是心梗吗」  │
│ · PII 脱敏：手机号 / 身份证 / 邮箱 / 就诊号   │
└─────────────────────────────────────────────┘
   │               │
   │ 命中危急      │ 非危急
   ▼               ▼
固定急救话术    意图分类（四类）
（不调模型）    ├ 知识库问答 → RAG 召回 + 生成
                ├ 院内业务 → HTTP 工具调用
                ├ 症状导诊 → 模板 / 转人工
                └ 闲聊问候 → 模板直出（不调模型）
                     │
                     ▼
┌─ 出口：合规校验（代码节点）─────────────────┐
│ · 6 类禁用表述正则拦截：用药推荐 / 剂量描述 /│
│   诊断性表述 / 绝对化承诺 / 处方性表述…      │
│ · 命中 → 整条拦截拒答                        │
│ · 通过 → 强制追加免责声明（代码追加，非提示词）│
│ · 剥离 <think> 思维链，避免患者看到推理过程  │
└─────────────────────────────────────────────┘
```

### 三个关键设计决策

**1. 为什么用规则判危急，不全交给模型？**
漏判代价不对称——漏掉一个心梗描述的代价，远大于误报一次。
规则能做到零漏判，模型用来降误报，两者配合而不是二选一。

**2. 为什么免责声明用代码强制追加？**
提示词是"请求"，模型可以不听；代码是"保证"。
医疗产品里，"应该不会说"和"结构上不可能说出来"是两回事。

**3. 为什么按任务拆模型？**
判定类任务要稳定和便宜（轻量模型 + 低温），生成类任务要表达质量（强模型）。
另外高频导诊问法直接走模板，不调模型——更快、零幻觉、成本几乎为零。

## 实测：8 条路径全部通过

| # | 场景 | 预期 | 结果 |
|---|------|------|------|
| 1 | 危急真阳性 | 固定急救话术，并报出命中信号 | 通过 |
| 2 | 院内业务查询 | HTTP 工具调用返回指引 | 通过 |
| 3 | 知识库命中 | 召回后结构化生成 | 通过 |
| 4 | 知识库未命中 | 兜底并声明"未查询到本知识库资料" | 通过 |
| 5 | 越界要求开药 | 诊疗边界拒答 | 通过 |
| 6 | 闲聊 | 模板引导话术，未调用大模型 | 通过 |
| 7 | 否定语境（"没有胸痛"） | 不误判为危急 | 通过 |
| 8 | 罕见病 | 转人工 | 通过 |

## 部署

### 1. 导入工作流

在 Dify 中「导入 DSL」，选择 `医疗AI-Workflow-安全增强版.yml`。
`医疗AI-Workflow-原始版本备份.yml` 是重构前的版本，仅用于对比或回滚。

### 2. 启动院内业务模拟接口（可选）

工具调用分支需要一个后端。仓库附了 Mock 服务：

```bash
python hospital_mock_server.py     # 监听 18080
# 或双击 启动Mock服务.bat
```

未启动时会走兜底文案而不是报错。

### 3. 本地 Dify 访问宿主机服务（可能遇到）

Dify 的 HTTP 节点走 ssrf_proxy，默认拦截私有网段。若报连接失败，
在 `docker/.env` 追加并重启代理容器：

```ini
SSRF_PROXY_ALLOW_PRIVATE_DOMAINS=host.docker.internal
SSRF_PROXY_ALLOW_PRIVATE_IPS=192.168.65.254
```

```bash
docker compose up -d --force-recreate ssrf_proxy
```

## 已知限制

- **知识库内容是最大的短板**：现有 4 个知识库共 141 个分段，内容偏政策文件与专家共识，
  与"咳嗽挂什么科"这类高频导诊问法不匹配，导致召回不到。这是**内容问题而非流程问题**，
  正确解法是补充"症状 → 科室"对照内容，而不是盲目调低相似度阈值。
- 知识库当前为 economy 索引，语义召回偏弱，可升级为 high_quality 索引。
- 单轮问答设计，未做会话级多轮；若需多轮应改为 Chatflow 类型应用。
- 本项目为演示用途，不构成任何医疗建议。
